# Touchline

Рабочее место спортивного аналитика: видео, аудио и документы → единые сегменты → OpenAI dense + Qdrant lexical → RRF → LLM reranker → соседние эпизоды → потоковый ответ с источниками.

## Быстрый запуск на Windows

Требования: Python 3.11–3.13, [uv](https://docs.astral.sh/uv/), Node.js 22+. Для видео и аудио нужны `ffmpeg` и `ffprobe` в PATH или абсолютные пути в `.env`.

```powershell
Copy-Item .env.example .env
# Заполните OPENAI_API_KEY в .env. Не добавляйте этот файл в Git.
uv sync --frozen --extra dev
Set-Location frontend
npm.cmd ci
npm.cmd run build
Set-Location ..
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Откройте [приложение](http://127.0.0.1:8000) или [OpenAPI](http://127.0.0.1:8000/docs). Без ключа интерфейс открывается, а загрузка и генерация возвращают понятную ошибку; фиктивных AI-ответов нет.

Без `QDRANT_URL` используется **настоящий embedded Qdrant**, сохраняемый в `data/qdrant`. Это удобный локальный режим для одного процесса. Для отдельного сервера задайте `QDRANT_URL=http://localhost:6333` или используйте Compose.

```powershell
# Нужен запущенный Docker Engine. .env должен существовать.
docker compose up --build -d
```

Compose поднимает Qdrant отдельно, хранит данные в volumes и публикует приложение только на `127.0.0.1:8000`. FFmpeg включен в образ приложения. Сервис перезапускается, если Qdrant еще не готов при первом старте. На публичном сервере нужны HTTPS, `APP_TOKEN` и ограничения загрузок/частоты запросов на reverse proxy. Это одно общее пространство, не многопользовательский SaaS: все обладатели токена видят одну библиотеку и историю.

## Работа

В библиотеке кнопка **Delete** удаляет выбранный исходный файл, его сегменты из Qdrant, кэш анализа и запись SQLite. Обработка этого файла отменяется; копии его доказательств убираются из истории, тексты прежних ответов сохраняются. Удаление требует подтверждения имени файла. При сбое повторите удаление; после перезапуска незавершённая очистка возобновляется. API: `DELETE /api/contents/{content_id}`.

1. Добавьте материал. Поддерживаются TXT, MD, PDF с текстовым слоем, DOCX, HTML, CSV, JSON, SRT/VTT как документы; MP4/MOV/MKV/WebM; MP3/WAV/M4A/OGG/FLAC/AAC.
2. Укажите идентификатор матча, команды и при необходимости тайм, игроков, смещение часов матча. Через API доступны также сезон и ссылка на источник. Имена и транслитерации можно внести вместе: `Mbappé, Мбаппе`.
3. Дождитесь статуса «Готово». Очередь сохраняется в SQLite. После сбоя можно нажать «Повторить»; после перезапуска незавершенное задание запускается заново.
4. Выберите материалы в библиотеке или ищите по всем готовым материалам. Уточняющие вопросы используют историю разговора.
5. Нажмите номер источника в ответе. Откроется текст или плеер с временем файла, кнопками ±30 секунд и соседними сегментами. Браузер должен поддерживать кодек исходного медиа; MP4/H.264/AAC и MP3 — рекомендуемые форматы для воспроизведения.

**Инкогнито:** запросы, ответы и история не записываются в SQLite; текущий диалог остается только в памяти вкладки. Все вызовы генерации отправляются с `store=False`. Данные всё равно передаются OpenAI; это не обещание отсутствия хранения со стороны провайдера. Загрузка файлов всегда добавляет их в общую библиотеку — об этом сказано в форме загрузки. Обычные завершенные ответы сохраняются вместе с источниками. Незавершенная генерация не сохраняется.

## Устройство retrieval

Одна collection `content_segments`, один point на `segment_id` (детерминированный UUIDv5 от `content_id` и порядкового номера):

| Часть point | Содержимое |
|---|---|
| `semantic` | OpenAI `text-embedding-3-small`, 1536 измерений, cosine |
| `lexical` | Unicode unigrams + bigrams, log-TF, corpus IDF в Qdrant |
| payload | content/segment IDs, тип, индекс, timestamps, transcript, visual/audio description, матч, команды, игроки, турнир, сезон, тайм, страница, источник, версия индекса |

Dense вектор объединяет текстовые представления модальностей. Sparse индексирует тот же текст, включая спортивные metadata. Unicode-нормализация сохраняет счет `2:1`, время `63:18`, номера и нормализует диакритику. Это lexical retrieval с хешированием признаков, **не BM25 и не строгий поиск фразы**: порядок соседних слов усиливается bigram-признаками, возможны редкие 32-bit hash collisions. Русско-латинские варианты имен поддерживаются metadata и query expansion, а не гарантированной автоматической транслитерацией.

Query planner разрешает ссылки на предыдущие вопросы и строит до четырех дополнительных запросов. Исходный запрос всегда сохраняется. Каждый запрос проходит dense и sparse поиск top-30. Все ранжированные списки объединяются через `Σ 1/(60 + rank)`; similarity scores разных поисков напрямую не складываются. Получившиеся top-20 оценивает OpenAI LLM reranker, учитывая соседние свидетельства. Это полноценный listwise reranker, не локальный cross-encoder. Для локального вопроса ответ использует до 6 главных сегментов (настраивается 1–8) и соседей ±15–30 секунд.

Вопросы обо всех голах, результате, победителе или матче целиком идут по отдельной ветке: все готовые сегменты выбранных источников читаются из Qdrant постранично и передаются в хронологическом порядке. Top-k здесь не ограничивает охват. Лимит — 1200 сегментов и 100000 токенов свидетельств. При нехватке контекста приоритет имеют концовка и голевые события; ответ и интерфейс отмечают неполный охват. Coverage означает охват загруженного файла, а не всех событий реального матча.

Для хоккея и футбола вопросы о голах используют отдельную последовательность изменений табло. Повторные кадры и празднования не увеличивают число голов. Итог берётся из наблюдения с явной финальной графикой, а не из суммы результатов поиска. Модель заполняет фиксированные поля объяснений для каждого перехода счёта; новые голы или счёт в структурированный результат добавить нельзя. Ссылки проверяются по разрешённым источникам. Время эпизода берётся из наблюдений кадров, а не генерируется моделью. Ошибки чтения табло всё ещё возможны; откаты и скачки счёта не превращаются в выдуманные голы.

Для других вопросов длинная хронология разбирается по частям (~8500 токенов) с сохранением исходных номеров ссылок, затем формируется общий ответ. Это необходимо и для лимитов API: большой контекст модели не означает высокий лимит токенов в минуту на аккаунте. Головые объяснения также получают ограниченные окна контекста. В интерфейсе coverage показывает охват прочитанного индекса, а не количество кадров, которые напрямую получил финальный LLM-запрос.

Routing выбирает приоритет transcript / visual / audio для расширения запроса и reranker; отдельные веса векторов модальностей в v1 не используются. Фильтры `content_ids`, `match_id`, готовность и версия индекса применяются ко всем веткам поиска. Соседи ограничены **тем же `content_id`**, для документов — предыдущим и следующим логическим сегментом. Перед генерацией контекст дедуплицируется и ограничивается токенами. Лимит включает metadata и текст свидетельств. Отсутствие релевантных кандидатов приводит к отказу от необоснованного ответа.

## Обработка файлов

- Документы: извлечение текста/таблиц → небольшие смысловые единицы → batch embeddings → объединение близких соседних единиц по cosine и границам страниц → финальные embeddings и sparse → batch upsert.
- Видео: фиксированные временные сегменты по 6 секунд; ASR 10-минутными блоками работает одновременно с визуальным анализом. Кадры анализируются каждую секунду (VIDEO_FPS=1), с перекрытием по секунде на границах и дополнительным кадром конца окна. Метки кадров — номинальная сетка ресэмплинга, а не точное время контакта шайбы. Настройки SEGMENT_SECONDS=6 и FRAME_OVERLAP_SECONDS=1. Структурированный визуальный анализ сохраняет вид спорта, показания табло, период, игровые часы, события и признаки повтора. VIDEO_FPS=2 повышает плотность и стоимость, но не заменяет трекинг. Whisper `verbose_json` интервалы пересекаются с общей timeline; речь может присутствовать в двух сегментах при пересечении границы.
- Аудио: Whisper и общая timeline. Опционально `AUDIO_EVENTS=true` включает анализ неречевых событий через модель `gpt-audio` для каждого сегмента. Это дополнительные оплачиваемые запросы.
- Embeddings отправляются пакетами до 64 текстов, не по одному chunk. Upsert также пакетный. Есть общие семафоры для модельных запросов и FFmpeg, временные файлы удаляются, subprocess завершается при отмене.
- До завершения обработки points имеют `state=staged` и скрыты от поиска. Затем весь контент переводится в `ready`. Повтор использует те же segment IDs и не размножает points. Успешные ASR-блоки и визуальные окна сохраняются в data/checkpoints и переиспользуются при повторе с тем же файлом, моделью и параметрами. Незавершённый запрос и опциональные audio events могут оплачиваться повторно. POST /api/contents/{id}/reindex запускает новую обработку готового или ошибочного источника; старые источники автоматически не становятся плотнее.
- Версия embedding-модели/размерности и lexical schema проверяется при запуске. При изменении задайте новую collection и переиндексируйте материалы; несовместимые векторы не смешиваются.

## Оценка

```powershell
uv run pytest -q
uv run ruff check app tests evaluation
uv run ruff format --check app tests evaluation
Set-Location frontend
npm.cmd run build
# При запущенном сервере на :8000:
npx.cmd playwright install chromium
npm.cmd test
```

Backend-тесты используют реальный локальный Qdrant и тестовые двойники OpenAI. Они проверяют поиск, фильтры, границы времени, batch/upsert, повторную обработку, SSE, историю, ошибки и инкогнито. Browser-тесты проверяют интерфейс с перехваченными API-ответами; это не измерение качества моделей.

`evaluation/corpus.json` и `evaluation/sports.jsonl` — небольшой **синтетический**, явно вымышленный спортивный corpus и размеченные вопросы. Есть factual, temporal, tactical, visual, statistical, causal, multi-hop, player, episode, multiple-sources, unanswerable; разделены dev/test. Gold labels привязаны к реальным ID сегментов этого corpus.

```powershell
uv sync --frozen --extra dev --extra eval
# Требует OPENAI_API_KEY. Делает оплачиваемые вызовы.
uv run python -m evaluation.run --live --split test --ragas
```

Создается отдельная collection `<QDRANT_COLLECTION>_evaluation`. Harness сравнивает dense, sparse, hybrid, hybrid + reranker с **одним query plan на вопрос**, до добавления соседей: Recall@K, Precision@K, MRR, NDCG@K, Hit Rate@K и средняя задержка. Затем оцениваются реальные сгенерированные ответы: RAGAS faithfulness, response/answer relevancy, context precision with reference и context recall. Результаты записываются в `evaluation/results/`; в репозитории нет выдуманных метрик качества. Набор мал для статистически надежных выводов; для приемки нужны размеченные пользователем реальные матчи и ручная проверка causal/visual выводов.

## Границы первой версии

Это запускаемая первая версия, а не доказанный эксперт по любому моменту матча. Один кадр в секунду не заменяет player/puck/ball tracking: быстрое касание или рикошет между кадрами может быть пропущено. Здесь нет автоматической идентификации игроков, OCR сканов, детектора логических границ атак или автоматического сопоставления часов матча и файла. Доступна временная сегментация; scene-aware/possession-aware границы — следующий этап для более точной спортивной аналитики. Система описывает наблюдения и маркирует неопределенность, но качество модели требует проверки на реальном видео.

Очередь долговечна для **одного worker-процесса**, без распределенных leases и checkpoints отдельных модельных стадий. Не запускайте несколько Uvicorn workers или реплик приложения на одной SQLite/embedded Qdrant. Отдельный Qdrant-сервер поддерживается; для горизонтального масштабирования самого ingestion понадобятся внешняя очередь и общее объектное хранилище. Нет полноценного учета денежных расходов, административной панели и автоматической очистки оригинальных файлов.

### Gemini для ответов

В `.env` задайте `CHAT_PROVIDER=gemini`, `GEMINI_API_KEY` и `GEMINI_MODEL=gemini-2.5-flash`. Ключ создаётся в [Google AI Studio](https://aistudio.google.com/apikey). После изменения `.env` перезапустите сервер. Endpoint Google уже задан в коде; отдельный адрес ресурса или deployment не нужен.

Gemini формирует финальные ответы и структурированные объяснения голов. Потоковые ответы и JSON-схемы передаются через [официальный OpenAI-совместимый API Gemini](https://ai.google.dev/gemini-api/docs/openai). Модель можно заменить через `GEMINI_MODEL`; [список моделей Google](https://ai.google.dev/gemini-api/docs/models).

`OPENAI_API_KEY` остаётся нужен для embeddings, Whisper, анализа кадров, планирования, reranking и промежуточных сводок. Индекс и загруженные материалы не меняются; переиндексация не требуется. Без ключа Gemini приложение показывает ошибку настройки и не переключается на OpenAI автоматически. Для явного выбора OpenAI используйте `CHAT_PROVIDER=openai` и `CHAT_MODEL`.

Ключи и настройки прежнего провайдера удалены из локальной конфигурации. Это не отзыв ключей в облачном аккаунте.

### Выбор источников

Новая загрузка автоматически становится выбранным источником. Выбор сохраняется в браузере; имя файла видно над полем вопроса. Флажками Library можно явно выбрать несколько файлов. Кнопка Use all sources включает анализ всей библиотеки. Пустой выбор в интерфейсе не запускает анализ; в API запрос без content_ids по умолчанию выбирает последний загруженный источник. Для всей библиотеки API требует all_sources=true. Если выбранный или последний файл ещё обрабатывается, сервер не подменяет его другими видео.
